# 1. 서비스 선정

## 1.1 어떤 서비스의 장애를 자동 복구할 것인가?

**서비스 이름:** AI 귀갓길 안심 도우미의 경로·안전정보 조회 서비스

**한 문장 설명:**

> 사용자가 출발지·도착지·이동 조건을 입력하면, 서비스는 보행 경로 후보와 확보 가능한 안전정보를 비교하고 근거와 한계를 설명하며, 사용자가 원할 경우 공식 안심서비스 앱의 신청 절차로 연결한다.

**정상 실행 흐름:**

```text
사용자
  ↓ 출발지·도착지·도착/출발 시각·경로 선호 입력
[경로 제공 서비스에서 보행 경로 후보 조회]
  ↓
[범죄주의구간 WMS 및 확인 가능한 안전시설 정보 조회·표시]
  ↓
정상 결과: 경로별 보행시간·안전정보·데이터 기준시각·추천 근거와 한계,
           선택적인 공식 안심서비스 앱 연결
```

**핵심 의존 서비스:**

| 의존 대상 | 용도 | 실패 시 영향 | 모의 구현 여부 |
|---|---|---|---|
| 행정안전부 생활안전지도 범죄주의구간(전체, WMS) | 지도에 범죄주의구간 레이어 표시 | 레이어 누락 또는 최신성 확인 불가. 해당 정보에 근거한 비교를 중단하고 오류·한계를 표시 | 장애 재현을 위한 모의 응답 준비. 실제 WMS 주소·접근조건·응답 형식은 확인 필요 |
| 보행 경로·지도 제공 서비스 | 보행 경로 후보와 예상 이동시간 조회 | 경로 비교 불가. 안전 경로인 것처럼 대체 경로를 임의 생성하지 않음 | 장애 재현을 위한 모의 응답 준비. 제공자·API 키·약관은 미결정 |
| 조명·비상벨 등 안전시설 데이터 | 경로 주변의 확인 가능한 시설 정보 표시 | 시설 정보 미표시 또는 일부 정보 누락. 미확인을 시설 부재로 단정하지 않음 | 공개 데이터 출처·갱신주기 확인 후 결정. 장애 주입은 모의 가능 |
| 공식 서울시 안심서비스 앱·안심이 신청 절차 | 사용자가 원할 때 공식 안내 또는 앱으로 이동 | 앱 이동 기능을 숨기거나 공식 안내 페이지를 표시 | 앱 딥링크·공식 URL 확인 전까지 링크는 미결정 |

## 1.2 서비스가 멈추면 어떤 영향이 발생하는가?

### 사용자 영향

- 경로 후보, 안전 레이어 또는 안전시설 정보를 확인하지 못해 귀가 계획을 세우기 어려울 수 있다.
- 오래되거나 누락된 정보를 완전한 안전 정보로 오인하면 실제 위험을 과소평가할 수 있다. 서비스는 안전을 보장하거나 긴급 대응을 대체하지 않는다.

### 운영 영향

- 외부 데이터 제공자의 장애와 내부 서비스 장애를 구분하기 어려울 수 있다.
- 반복 호출이 외부 제공자 부하를 키우거나 장애를 장기화할 수 있다.

### 데이터·비용·보안 영향

- 출발지·도착지는 민감한 위치정보가 될 수 있다. MVP에서는 서버 저장·장기 로그 기록을 하지 않고, 장애 로그에서 위치와 API 키를 제거한다.
- 외부 지도 API의 호출 제한이나 요금이 발생할 수 있다. 제공자와 한도는 미결정이며, 제한을 초과하는 자동 재시도는 금지한다.

### 심각도

- [ ] 낮음 — 지연되지만 핵심 기능은 유지됨
- [ ] 중간 — 일부 요청이 실패하고 운영자 대응이 필요함
- [x] 높음 — 부정확한 안전정보나 경로 설명이 사용자 판단에 영향을 줄 수 있음

**선택 근거:** 단순한 일시 중단보다 잘못된 안전정보를 신뢰하는 상황이 더 큰 위험이다. 데이터가 없거나 최신성을 확인할 수 없으면 안전하다고 표현하지 않고, 정보 누락을 명시한다.

## 1.3 현재 사람은 장애를 어떻게 발견하고 복구하는가?

현재 운영 중인 제품이나 수동 대응 절차는 제공되지 않았다. 아래는 MVP 운영 시 적용할 수동 기준안이다.

| 단계 | 현재 사람의 행동 | 사용하는 정보·도구 | 소요시간 | 문제점 |
|---|---|---|---:|---|
| 탐지 | [미정] MVP에서는 상태 확인 요청과 오류 로그 확인 | 의존 서비스별 상태·오류율 | [미정] | 모니터링 기준이 없으면 사용자 오류 신고 전까지 지연될 수 있음 |
| 진단 | 제공자 오류인지 앱 내부 오류인지 확인 | 요청 시각, 의존 서비스 코드, 비민감 오류 로그 | [미정] | 위치·인증정보가 로그에 포함되지 않도록 해야 함 |
| 복구 | 정상화 대기 후 제한된 재요청, 또는 해당 정보 표시 중단 | 사전 허용된 재시도 정책 | [미정] | 임의 설정 변경·외부 운영기관 개입은 범위 밖 |
| 검증 | 같은 기능의 상태·샘플 요청·데이터 유효성 확인 | 독립 헬스체크 및 기능 테스트 | [미정] | 복구 컴포넌트의 자체 성공 보고만으로 완료할 수 없음 |
| 보고 | 장애 원인 후보, 시도, 검증 결과를 운영자에게 전달 | 사건 기록 | [미정] | 개인정보와 비밀정보 제거가 필요 |

**자동화하려는 단계:** 의존 서비스 감시, 장애 유형 분류, 허용된 제한 재시도, 회로 차단, 복구 후 독립 검증, 비민감 사건 기록.

**사람이 계속 담당해야 할 단계:** 원인 불명 장애 판단, 운영 설정·자격증명 변경, 공식 데이터·신청 정책 해석, 사용자 안전 관련 최종 판단.

## 1.4 3일 동안 재현 가능한 최소 서비스는 무엇인가?

### 포함 범위

- 모바일 우선 반응형 웹의 귀가 조건 입력 및 경로 후보 비교 화면.
- 공공 범죄주의구간 WMS의 실제 연동 가능성 확인. 경로·안전시설 제공자가 확정되지 않거나 접근할 수 없으면 미결정/장애로 표시하고 모의 제공자로 장애를 재현.
- 경로 시간·조건과 실제로 조회된 안전정보에 근거한 설명. 위험 점수나 안전 보장은 제공하지 않음.
- 사용자의 선택에 따른 검증된 공식 안심서비스 안내·앱 이동 연결.
- 세 가지 이상의 의존 서비스 오류와 앱 프로세스 중단을 테스트 환경에서 반복 주입하고 제한적 자동 복구·독립 검증.

### 제외 범위

- 실제 긴급신고, 구조 요청, 실시간 관제, 자동 동행 예약 제출.
- 사용자 계정, 결제, 위치 이력 저장, 개인화 프로파일링.
- 공공기관의 동행 가능 여부·자격 판정 또는 예약 확정.
- 확인되지 않은 데이터로 범죄 위험 점수, 안전 순위 또는 조명 유무를 추정.
- LLM이 생성한 임의 명령 실행, 운영 시스템·운영 데이터 변경, 비용 제한 없는 재시도.

# 2. 에이전트 설계

## 2.1 장애를 탐지하는 주체는 누구인가?

**에이전트 이름:** Monitor (규칙 기반 모니터)

**관찰 데이터:**

- [x] 헬스체크 응답
- [x] 애플리케이션 로그
- [x] 오류율
- [x] 응답시간
- [x] 프로세스 상태
- [ ] 기타

**장애 판정 조건:** 사전 정의된 타임아웃 초과, HTTP 5xx, 연결 오류, 필수 응답 누락·형식 오류, 허용된 테스트 프로세스의 중단. 실제 서비스 기준 임계값은 API 제공자 확인 후 확정한다.

**출력 메시지:** `incident_id`, 의존 서비스 식별자, 실패 코드, 감지 시각, 비민감 근거, 시도 횟수를 포함한 사건 레코드.

## 2.2 원인을 진단하는 주체는 누구인가?

**에이전트 이름:** Diagnosis (규칙 기반 분류기)

**입력:** Monitor 사건 레코드, 상태 확인 결과, 비민감 오류 코드.

**분류할 장애 유형:**

| 장애 코드 | 설명 | 판단 근거 | 신뢰도 또는 규칙 |
|---|---|---|---|
| `UPSTREAM_5XX` | WMS·경로·시설 데이터 제공자의 서버 오류 | HTTP 5xx 상태 | 규칙 일치 시 확정 |
| `UPSTREAM_TIMEOUT` | 의존 서비스의 응답 지연 | 설정된 요청 제한시간 초과 | 규칙 일치 시 확정 |
| `UPSTREAM_EMPTY_OR_INVALID` | 비어 있거나 파싱할 수 없는 응답 | 스키마·필수 필드 검사 실패 | 규칙 일치 시 확정 |
| `DEPENDENCY_UNREACHABLE` | 네트워크 연결 또는 이름 해석 실패 | 연결 오류 | 규칙 일치 시 확정 |
| `APP_PROCESS_DOWN` | 허용된 로컬 테스트 프로세스 중단 | 프로세스 상태 확인 | 프로세스 식별자 허용목록 일치 시 확정 |
| `UNKNOWN` | 위 규칙으로 분류할 수 없는 장애 | 근거 불충분 또는 충돌 | 자동 변경 금지, 사람에게 전달 |

**원인을 판단할 수 없을 때 행동:** 복구를 실행하지 않고, 증거와 `UNKNOWN` 상태를 기록해 운영자 검토를 요청한다.

## 2.3 복구를 실행하는 주체는 누구인가?

**에이전트 이름:** Recovery (허용목록 기반 함수)

**허용된 복구 행동:**

- 일시적 의존 서비스 오류에 대해 사건별 최대 3회, 백오프 간격 1·2·4초로 제한 재시도한다. 실제 제공자 제한과 정책에 따라 조정 전 검토가 필요하다.
- 실패한 안전정보 레이어는 숨기고 데이터 미수신·최신성 확인 불가를 표시한다. 경로 정보만 남더라도 안전 우위 경로라고 표현하지 않는다.
- 로컬 실습에서 허용목록에 등록된 모의 제공자 프로세스만 재시작한다.

**금지된 행동:**

- LLM 생성 명령·임의 쉘 실행, 허용목록 외 프로세스 재시작.
- 운영 설정·인증정보·데이터 변경, 사용자 위치를 로그에 남기는 행위.
- 장애 원인 불명 상태에서의 자동 변경, 외부 제공자에 대한 무제한 재시도.
- 복구 검증 없이 정상화 선언.

**필요한 도구·API·명령:** 의존 서비스의 제한된 HTTP 클라이언트, 애플리케이션 헬스체크, 실습용 프로세스 관리자. 구체 기술·API는 미결정.

## 2.4 복구 성공을 독립적으로 검증하는 주체는 누구인가?

**에이전트 이름:** Verification (Recovery와 분리된 읽기 전용 검사기)

**독립성이 필요한 이유:** Recovery의 자체 실행 성공 메시지와 실제 사용자 기능의 정상 동작을 구분하기 위해서다.

**검증 항목:**

- [x] 헬스체크 정상
- [x] 핵심 기능 테스트 통과
- [ ] 오류율 정상 범위
- [ ] 응답시간 정상 범위
- [ ] 데이터 무결성 확인
- [x] 회귀 테스트 통과

추가 확인: 응답 스키마 유효성, 데이터 기준시각·출처 표시, 장애 시 안전정보 누락 안내, 위치·비밀정보 미기록.

**복구 실패 판정 조건:** 헬스체크 또는 핵심 기능 검증 실패, 데이터 검증 실패, 상한 내 재시도 소진, 회로 차단 상태.

## 2.5 오케스트레이터가 필요한가?

- [x] 필요함
- [ ] 필요하지 않음

**판단 근거:** 감지→진단→제한된 복구→독립 검증의 순서, 재시도 상한, 회로 차단과 사람 이관을 강제해야 한다. 별도 LLM일 필요는 없으며 결정적 상태기계로 구현한다.

### 오케스트레이터의 책임

- 사건별 상태·시도 횟수·전체 타임아웃 관리.
- 허용된 복구 함수만 호출하고 검증 결과에 따라 완료 또는 에스컬레이션.
- 회로 차단, 냉각시간, 중복 사건 억제.

### 오케스트레이터가 해서는 안 되는 일

- 정책·권한·재시도 상한 우회, 복구를 검증 없이 성공 처리.
- 위치·개인정보를 추가 수집하거나 임의 명령을 생성·실행.

# 5. 검증

## 5.1 복구 성공을 어떤 지표로 판정할 것인가?

| 지표 | 정상 기준 | 측정 위치 | 실패 기준 |
|---|---|---|---|
| 헬스체크 | 테스트 환경에서 정상 응답 | 의존 제공자·앱 헬스 엔드포인트 | 제한된 검사에서 계속 실패 |
| 오류율 | 정상 시나리오에서 5xx·연결 실패 0건 | 모의 제공자·앱 요청 로그 | 테스트 완료 후 오류 지속 |
| 응답시간 | 경로 제공자 타임아웃 안에 응답 | 클라이언트/제공자 어댑터 | 타임아웃 초과 |
| 핵심 기능 테스트 | 입력 검증·경로 비교·누락 데이터 안내 통과 | 통합 테스트 | 하나라도 실패 |
| 회귀 테스트 | 장애 회복 후 비장애 데이터 표시·리다이렉트 기능 통과 | 테스트 러너 | 기존 기능 실패 |
| 안전정보 정확성 | 출처·기준시각·누락 여부가 표시되고 안전 보장 표현이 없음 | 화면 검사·테스트 | 누락 정보를 안전으로 표시 |

**데모 목표(초안):** 주입 가능한 3개 이상의 의존 장애 유형을 각각 반복 재현하고, 허용된 오류만 상한 내 복구하며, 검증 실패 시 성공으로 기록하지 않는다. MTTD 5초 이내·복구 실행시간 15초 이내를 모의 로컬 환경 목표로 측정한다. 실제 공공 API 가용성은 성공 기준으로 보장하지 않는다.

## 5.2 장애 탐지부터 복구까지 걸린 시간을 어떻게 측정할 것인가?

```text
injected_at  = 장애 주입기가 기록한 시각
detected_at  = Monitor가 사건을 생성한 시각
recovery_started_at = Recovery 실행 시작 시각
recovered_at = 독립 검증 통과 시각
```

```text
MTTD = detected_at - injected_at
MTTR = recovered_at - injected_at
복구 실행시간 = recovered_at - recovery_started_at
```

**시간을 기록할 컴포넌트:** 모의 제공자 장애 주입기와 Orchestrator의 사건 기록.

**시간 형식과 타임존:** UTC ISO 8601. UI 표시 시 사용자 지역 시간으로 변환.

**로그 보존 기간:** MVP 실행 종료까지의 임시 보존. 운영 보존 기간은 미결정.

## 구현하지 않을 것

1. 실제 긴급 대응, 동행 예약의 자동 제출 또는 지원 가능 여부의 자체 판정.
2. 미검증 데이터 기반의 위험 점수·안전 보장·시설 부재 단정.
3. 위치정보 저장, AWS 운영 리소스 변경, 임의 명령 실행.

## 성공 기준

1. 경로·안전정보 중 어떤 데이터가 없거나 오래됐는지 사용자에게 명확히 표시한다.
2. 최소 3개 장애 유형에서 재시도 상한·회로 차단이 동작하고 검증 실패를 성공 처리하지 않는다.
3. 장애 주입·탐지·복구·검증 시각과 MTTD/MTTR을 재현 가능한 로그로 산출한다.

## 주요 위험과 대응
